# 记忆分层与约束：为什么这样设计

> 这份文件回答「为什么」——为什么要四层、为什么路径要按月份、为什么不全量注入、门禁为什么用脚本。
> 用户质疑某条规则、或你要改动体系本身时，先读这里。

## 前提：上下文是易失的，文件是持久的

任何长任务都会遇到：上下文被压缩、会话重开、换了一个 agent、换了一个人接手。
这时"当时讨论过什么"已经完全不可靠（甚至是被压缩后的错误总结）。
所以体系的**第一性原则**：**凡是下个会话还需要知道的东西，必须在文件里，且可被找到。**

推论一：**日志要按任务切分，而不是按天流水**。按天流水会把多个任务混在一篇里，无法独立引用、无法判断完成度。
推论二：**日志不能只是 diff 的复述**。diff 里没有"为什么"，而"为什么"才是下次真正需要的东西。
推论三：**必须有索引**。文件多了以后，"知道存在但找不到"等于不存在。

## 四层为什么不能合并

| 层 | 时间尺度 | 更新方式 | 如果合并会怎样 |
|----|----------|----------|----------------|
| 日志 | 一次任务 | 只追加 | 混进知识库 → 知识库被任务细节淹没，检索噪声剧增 |
| 知识 | 长期，可被推翻 | 原地改 | 混进日志 → 结论散在几十篇日志里，没人会去翻 |
| 领域 | 长期，业务事实 | 原地改 | 混进知识库 → 技术结论与业务规则同层，agent 分不清"这是必须遵守的业务规则"还是"这是某个技巧" |
| 约束 | 与体系同寿 | 随体系演进 | 不显式声明 → 全靠自觉，必然烂 |

关键区别是**"能否被推翻"**：日志记录的事实不可推翻（当时确实这么做的）；
知识是当下的最优解（会过时）；领域规则是被业务方定义的（会变）。

## 路径为什么是"日期的纯函数"

约定：`docs/daily/<YYYY-MM>/YYYY-MM-DD_<slug>.md`，月份 = 日志日期所在月。

对比两种做法：

| | 平铺 + 事后归档 | 写入即定月份 |
|---|---|---|
| 归档动作 | 搬文件 + 批量改索引链接 + 改跨文档引用 | **无** |
| 出错方式 | 改漏一处链接 → 死链；月份与表格不一致 | 只可能"月份算错"，而这是脚本的行为 |
| 可校验性 | 需要对比"文件集合 vs 索引集合" | 同上（且路径自带月份，可交叉校验三处一致） |

历史教训（这个体系就是这么演化出来的）：某仓 54 篇 9 月日志事后归档时，索引 54 行 + 十几个跨文档引用要一起改；
漏一个就是死链。改成"写入即按月份"后，这类工作彻底消失。
**结论：把重复劳动消灭在规则里，而不是靠每次认真。**

推论：既然路径可推导，**索引行也应该可生成** → 所以 `new-daily-log.sh` 顺手把索引行骨架插进去。
人工只剩「回填工作内容/提交/备注」这件真正需要判断的事。

## 为什么门禁必须是脚本，不能是约定

约定会烂，因为违反约定的代价是"下次可能出问题"，而不是"现在立刻红灯"。
所以门禁的形态必须是**退出码**：

```bash
bash scripts/check-daily-index.sh --strict   # 缺索引行 / 死链 / 路径不符 / 重复索引 → 非零
```

它可以被挂在任何地方（pre-commit、CI、agent 的收尾清单），而 agent 的收尾清单本身也写进了 `AGENTS.md` 托管块
—— 这样"不写日志"从"道德要求"变成"任务未完成"。

**门禁只校验能机器判定的事**（结构一致性）；"日志写得好不好"不校验——那种门禁只会催生敷衍的填充。

## 为什么召回是非全量的

朴素想法是"把知识库塞进上下文"。问题：

1. 预算：知识库会长到几十万字，塞不进；塞一部分则"塞哪部分"成了新问题
2. 信噪比：真正相关的那 3 条会被 200 条不相关的淹没，模型注意力被摊薄
3. 时效：上下文里的是快照，文档更新后不会同步（文件不会）

所以：**用关键词把"该看哪份"精准推到台面上，由 agent 判断相关后再全量读文件。**
触发源用「prompt + `git diff --cached`」而不是只看 prompt：很多坑是在"你正要写的那段代码"里踩的，
用户 prompt 往往只说"改一下这个界面"，但 diff 里已经出现了出问题的字段。

## 约束为什么要写进 AGENTS.md

- 各家的 agent 都会读根 `AGENTS.md`（这是事实上的跨工具约定），所以它是**唯一一个"每轮都在上下文里"的位置**
- 但也会被人改 → 因此用 `<!-- KNOWLOG:START/END -->` 托管块划清边界：块内脚本生成、块外人工内容
- 同样理由：不要在 `CLAUDE.md` 里复制一份规则，只写一行指向托管块（两份真相必然漂移）

## 常见的"看起来更省事"的错误做法

| 做法 | 为什么坏 |
|------|----------|
| 把日志直接写在聊天里，收尾时再总结 | 收尾总结会丢细节，且压缩后的上下文已经在丢信息 |
| 日志只写"改了什么文件" | 下次看的人仍然不知道为什么、也不知道能不能改回去 |
| 一个任务写多个日志文件 | 破坏"一任务一篇"，索引与引用都变模糊 |
| 知识库按时间命名（`bug-0723.md`） | 下次遇到问题想不起来按日期查；名字要能反映问题 |
| 知识过期后新写一篇 | 两篇都"存在"，agent 会读到错的那篇 |
| 把领域规则放进知识库 | agent 会把"业务必须"降级成"某处的技巧" |
| 门禁只写"建议" | 会烂 |
| 全量注入知识库 | 淹没 + 预算爆炸 + 快照过期 |
