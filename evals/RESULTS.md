# 评测结论（evals）

> 这份文件回答一个问题：**这套 skill 到底有没有用？** 方法是"同一批任务，带 skill vs 不带 skill 各跑一遍，再看评分"。
> 逐次运行的 `grading.json` / `run_meta.json` / `transcript.txt` / `manual_review.md` 落在临时工作区（`${TMPDIR}/knowlog-iter4/`），**不随仓库保留**（体积大、且是运行产物）；
> 结论与复现命令见下面各节。跑法说明书在 `evals/README.md`。

## 1. 历史结论（iteration-1..3）

| 轮次 | skill 版本 | 用例特点 | 带 skill | 不带 skill（基线） |
|---|---|---|---|---|
| iteration-1 | v1 | 从零搭体系、记日志、体检修复 | **100%** | 76.7% |
| iteration-2 | v0.2.0 | 新增：采纳异构 `docs/`、单面项目 flat 布局 | — | — |
| iteration-3 | v0.3.0 | 刁钻：跨月补写、索引占位、散落日志、死链、布局混用 | 2 个用例 **0 差异** | 2 个用例 0 差异 |

基线失分集中在**体系完整性**（结构/索引/门禁），不在"会不会写文档"。

## 2. iteration-3 暴露的三个评测设计缺陷（已全部修）

| # | 缺陷 | 后果 | 修法（iteration-4，已实施） |
|---|---|---|---|
| 1 | **夹具里放了"已建好的体系"** | 两边都照抄现成结构 → **0 差异**，等于没测 | `evals/build_fixtures_v4.sh`：夹具只给**原始素材**（代码 + 散落/异构旧文档 + 刚做完的任务描述），不给现成体系（唯一例外 eval-9，原因见 `evals-v4.json` 的 `design_notes`） |
| 2 | **基线不干净**：以为"不带 skill"，其实全局装着，模型照样能读到 | "带 skill 更好"的结论偏乐观 | `evals/run_case.sh`：**机械隔离** —— 跑基线时把已安装 skill 临时改名移开 + `--disable-slash-commands` 双保险；移开失败**直接中止**（宁可没数据，不要假基线）；证据写进 `run_meta.json.isolation` |
| 3 | **只评"结构对不对"**，不评"写得好不好" | 会把"形状不同"误判成"质量更差" | `evals/review-rubric.md`：3 条人工维度（D1 日志重点 / D2 知识可复用 / D3 尊重既有约定，各 0–2 分）；`grade_v4.py` 自动生成 `manual_review.md` 骨架 |

## 3. 结果（eval-7..9：三个用例，带/不带各跑一次）

| 用例 | 它测什么 | 结构断言 | 人工量表 |
|---|---|---|---|
| eval-7 全新项目（连 `docs/` 都没有） | 从零搭结构 | **9/9** vs **0/9** | **6/6** vs **5/6** |
| eval-8 一团乱的历史文档 | 归位/合并 + 补索引 + 识别死链 | **9/9** vs **6/9** | **6/6** vs **4/6** |
| eval-9 体系已就位 + 刚做完的任务 | 收尾质量（写日志/沉淀知识/同步索引） | **7/7** vs **7/7** | **6/6** vs **6/6** |
| **小计** | | **25/25（100%）** vs **13/25（52%）** | **18/18** vs **15/18（83%）** |

### 逐例解读（人话）

- **eval-7（差距最大）**：带 skill 建出完整体系（月份目录日志、by-end 知识库 + 两级索引、`domain context`、`scripts/` 且门禁 `--strict` 通过、`AGENTS.md` 托管块）。
  基线建了 `CLAUDE.md` + `docs/conventions.md` + `docs/dev-log.md` + `docs/pitfalls.md`（带 `P-001` 编号索引）+ 两套模板 —— **内容质量并不差（5/6）**，
  但它没有任何"能自动拦人"的东西：没有门禁、没有两级索引、没有月份目录。所以结构 0/9 这个数字**只说明"形状不同"**。
- **eval-8（差距具体）**：基线把两篇日志搬进了 `docs/daily/2026-09/`（显眼的搬家它做得对），但漏掉三件"不显眼却决定长期可用"的事：
  孤儿知识文档没归位也没登记、没有可运行的门禁、没有 `AGENTS.md` 托管块、也没给本次整理留一篇收尾记录（人工量表 D1/D2 各扣 1 分）。
- **eval-9（打平，重要发现）**：两边都照项目里既有的 `docs/template.md` 写出了同样的五段式日志与知识文档，基线甚至把真实提交 hash 填了进去（7/7、6/6）。
  → 这说明：**体系一旦装好，模板与钩子本身就把"收尾质量"拉齐了** —— 这个 skill 的增量主要在"**搭与整**"（eval-7/8），而不在"每次收尾都需要它"。

## 3b. 扩评结果（eval-10..12：补齐三类未被覆盖的能力）

> 夹具与用例定义见 `evals/evals-v4.json` / `evals/build_fixtures_v4.sh`；断言见 `evals/grade_v4.py`。
> eval-10/12 的夹具只给**原始素材**（代码 + 散落笔记 + 任务描述，**不预置体系**）；eval-11 例外（必须先有索引才谈得上"修"，已在 `design_notes` 备案）。

| 用例 | 它测什么 | 结构断言 | 人工量表 |
|---|---|---|---|
| eval-10 跨月补写 + 索引占位 | 日志按**任务日期**（而非今天）归月 + 索引行填实 | **10/10** vs **8/10** | **6/6** vs **4/6** |
| eval-11 索引漂移修复 | 用**项目自带门禁**定位并修好四类漂移（死链/月份不符/缺行/孤儿知识） | **9/9** vs **9/9** | **2/6** vs **2/6**（D3 并列；D1/D2 无落点） |
| eval-12 单面项目 flat + 关键词召回 | 不造端层 + 召回**真能命中**（不只是文件存在） | **11/11** vs **5/11** | **6/6** vs **4/6** |
| **小计** | | **30/30（100%）** vs **22/30（73%）** | **14/18** vs **10/18** |

### 逐例解读（人话）

- **eval-10（跨月真的被考到了，但差距在"约束"不在"写字"）**：prompt 明确说了"按各自发生的日期"，基线也确实把 9 月那篇放进了 `docs/daily/2026-09/2026-09-12_*.md`、
  新起了 `### 2026-09` 表格、行也填实了（10 项里过了 8 项）。它丢的两项恰好是**机器可校验的那层**：没有 `scripts/check-daily-index.sh` 门禁、没有 `AGENTS.md` 托管块。
  人工量表差在 **D2**：基线没有把"漏乘 `packaging` 会稳定差一个包装倍数"沉淀成知识（6 vs 4）。
  → 也就是说：**"跨月补写"这个动作，光靠 prompt 说明白，强基线也能做对**；skill 的增量仍落在"把它变成会被门禁拦住的约定"。
- **eval-11（打平，和 eval-9 同源）**：这个用例**必须自带体系**（没索引就无从修），于是门禁脚本也一并给了基线 —— 基线直接跑 `check-daily-index.sh` / `reindex-knowledge.sh` 就修好了（9/9、D3 2/2）。
  → 再次印证 eval-9 的发现：**增量在"搭与整"（把门禁带进来），不在"已有门禁时的使用"**。
  另一个诚实结论：**两配置都没给这次修复留收尾记录、也没沉淀"索引漂移的修法"**，所以人工量表在这里几乎没区分度（D1/D2 都 0，合计并列 2/6）。
- **eval-12（形状差异最典型，也最需要两把尺子）**：基线**自建了一套等价的轻量体系** —— `docs/{architecture,conventions,testing,development}.md` + `docs/knowledge/csv-export-column-order.md`
  + 它自己写的 `scripts/knowledge-retrieve.sh`（实测 `bash scripts/knowledge-retrieve.sh "csvColumns 列顺序"` **真能命中**，只是 CLI 契约不是 skill 的那一套）。
  结构断言 5/11 低，主要是**形状不同**（没有四个分类/根索引/`.keyword-map.json`/门禁/`AGENTS.md`）；人工量表 4/6 —— 它的知识文档质量很高（D2=2），但**没产出任务日志（D1=0）**。
  → 这正是 `README.md` 铁律 #3 说的：**只看客观断言，会把"形状不同"误判成"什么都没做"**；两把尺子一起看才不偏。
  （顺带修了一个评测自身的偏差：召回断言原先只认 skill 的 `--root` 调用形式，会把"自建了等价召回"的基线误判为"没有召回"——现已同时接受任务里给用户的原话形式 `bash scripts/knowledge-retrieve.sh "<probe>"`。）

### 一句话结论（扩评后）

**增量在「可校验的约束与索引」，不在「帮你写字」** —— 这条结论在补了三个用例后没有变，而且更具体了：

1. **写字质量两边都不差**（eval-10 基线 4/6、eval-12 基线 4/6，甚至自建了能用的召回）；差的是**机器可校验的那层**（门禁、索引、托管块、keyword-map）。
2. **一旦夹具自带体系与门禁，基线就追平**（eval-9、eval-11）→ 说明 skill 的价值集中在"**从 0 搭 / 把一堆乱的整成可校验的**"，而不是"日常每次都用它"。
3. **跨月补写这类"细规范"，光在 prompt 里说明白，强基线也能做对**（eval-10 基线 8/10）；但"必须落月份目录 + 索引行不许留占位 + 门禁拦得住"这套**可执行的约束**，只有 skill 带来。

### 合并总表（eval-7..12）

| | 结构断言 | 人工量表 |
|---|---|---|
| 带 skill | **55/55（100%）** | **32/36（88.9%）** |
| 不带 skill（隔离基线） | **35/55（63.6%）** | **25/36（69.4%）** |


## 3c. 模型对照（2026-10-19，本机 macOS · claude CLI 路由）

同一批 6 个用例、同一套夹具与隔离，只换模型重跑一遍（各自独立 workspace）：

| 用例 | 结构断言（`deepseek-v4-flash`，默认） | 结构断言（`deepseek-v4-pro`） |
|---|---|---|
| eval-7 全新项目 | 9/9 vs 0/9 | 9/9 vs 0/9 |
| eval-8 一团乱的历史文档 | 9/9 vs 6/9 | 9/9 vs 6/9 |
| eval-9 收尾（体系已装好） | 7/7 vs 7/7 | 7/7 vs 7/7 |
| eval-10 跨月补写 + 索引占位 | 10/10 vs 8/10 | 10/10 vs 8/10 |
| eval-11 索引漂移修复 | 9/9 vs 9/9 | 9/9 vs 9/9 |
| eval-12 单面 flat + 召回 | 11/11 vs 5/11 | 11/11 vs **0/11** |
| **合计** | **55/55（100%） vs 35/55（63.6%）** | **55/55（100%） vs 30/55（54.5%）** |

**怎么读**：

- **带 skill 的结果跨模型完全一致（55/55 ×2）**：形状稳定、可复现 —— 这正是"可校验的约束与索引"带来的性质。
- **不带 skill 的结果随模型浮动**（63.6% → 54.5%），差异全部出在 eval-12：两个基线**都**沉淀了知识、**都**自己写了召回脚本，
  但 `flash` 基线把知识放在 `docs/knowledge/` 且探针能命中（5/11），`pro` 基线放在了**仓库根 `knowledge/`**、
  且没有索引/关键词表/门禁（0/11）→ 断言（knowlog 形状）全灭。
- **人工量表抽查 eval-12（pro）**：基线 **5/6** vs 带 skill **6/6**。pro 基线的知识文档甚至带 `keywords/tags` frontmatter、
  症状/根因齐全 —— **它不是"做得差"，是"组织方式不同 + 没有机器可校验的层"**。这与 §2 缺陷 3 是同一个道理。
- 结论（更锋利了）：**skill 把"靠模型自觉"换成"靠结构约束"** —— 带 skill 时结果与模型无关；不带时，结果取决于模型那天选了哪套约定。

> 口径说明：本轮只跑客观断言（12 次运行）；人工量表**只抽查了出现差异的 eval-12**，其余与 flash 轮一致故未重复打分。
> 换模型/换 harness 请沿用同一 workspace 约定（见 `evals/README.md`「换模型做对照」）。

## 4. 已知干扰与教训（跑之前先看这节）

1. **第三方钩子会污染运行目录**：本机另一个记忆工具（`.remember/`）会在任何项目里写文件，
   它的记忆文件可能恰好包含断言搜索的关键词。
   → `grade_v4.py` 已把 `.remember/`、`.trellis/`、`node_modules/` 与评测自产文件列入 `IGNORE_DIRS/IGNORE_FILES`；
   跑正式评测时最好把这类钩子临时关掉。
2. **隔离是"临时改全局状态"**：基线运行期间 `~/.claude/skills/knowlog` 等会变成 `.hidden-<pid>`（宿主 harness 的 skill 列表会短暂变化），
   `run_case.sh` 用 `trap` 自动还原；`run_iteration4_pilot.sh` 开头/结尾也会兜一次。
   **若被强杀**：手工检查 `ls -d ~/.claude/skills/*.hidden-*`。
3. **模型会变**：本环境 `claude` CLI 实际路由到 `deepseek-v4-flash`（运行时会打印 `unrecognized_model` 警告），
   数字是"**该模型在该配置下**"的结果，换模型必须重跑，不能直接引用。
4. **断言误伤是最隐蔽的偏差**（本轮真踩到）：第一版 `grade_v4.py` 把索引**说明文字**里的 `<slug>` 当成"占位残留"，
   于是 eval-9 两边同时被扣分（7/7 → 6/7）——**误伤会同时压低两边，让结论看起来"都差不多"，从而掩盖真实差异**。
   修法：只检查表格行（`| ... |`）里的占位符。写断言时务必分清"说明文字"与"残留内容"。
5. **串行跑**：基线要动全局 skill，with/without 不能并行。
6. **复核时别把 grading.json 写到别处**（本轮真踩）：`grade_v4.py` 原来只按**输出路径**找夹具快照
   （`baseline_files.json`），复核时手滑写到 `/tmp` 会让快照找不到 → 所有"新增了什么"的断言**集体假红**
   （eval-9 一度被判 0/7）。已修：改为**离项目最近优先**（`PROJ.parent`），与输出路径无关。
6. **"形状不同"会被客观断言误伤**（扩评新增用例时踩到）：eval-12 的基线自建了一套等价的轻量体系
   （含它自己写的 `scripts/knowledge-retrieve.sh`，`bash scripts/knowledge-retrieve.sh "csvColumns 列顺序"` 实测能命中），
   但第一版召回断言只认 skill 的 `--root` 调用形式，于是把它判成"没有召回"。
   修法：断言同时接受**任务里给用户的原话形式**（`bash scripts/knowledge-retrieve.sh "<probe>"`，在项目目录里跑）与 `--root` 形式。
   教训：**断言要盯"能力有没有"，而不是"有没有用我们这一套 CLI 契约"**；否则客观分虚低，结论又变回"形状不同"。
7. **夹具自带体系 = 基线也能用**（eval-11 的必然结果）："修索引漂移"必须先有索引与门禁，所以夹具只能自带体系，
   而基线一旦也能读到门禁，就会和带 skill 打平（9/9 并列）。这不是评测缺陷，是**这个能力点的真实边界**
   —— 见第 3b 节结论 2。写这类用例时要在 `evals-v4.json` 的 `design_notes` 里备案，并在 `measures` 里写明"测的是修复能力，不是搭建能力"。

## 5. 复现命令

```bash
# ① 97 项确定性自测（不依赖模型，最快；CI 也跑这个）
bash evals/test_scripts.sh

# ② iteration-4：造夹具 + 六个用例 × 两配置，全部跑完并出对照表（串行，自带隔离残留修复）
#    注意：setup_iteration4.sh 会重建全部用例目录，pilot 开头也会调用它 ——

bash evals/run_iteration4_pilot.sh "${TMPDIR:-/tmp}/knowlog-iter4"

# 单跑某个用例（先造目录，再跑两次，再评分）
WS="${TMPDIR:-/tmp}/knowlog-iter4"; D="$WS/iteration-4/eval-8-messy-legacy-docs-adopt"
bash evals/setup_iteration4.sh "$WS"
bash evals/run_case.sh "$D/with_skill"    with_skill
bash evals/run_case.sh "$D/without_skill" without_skill
python3 evals/grade_v4.py eval-8 "$D/with_skill"    "$D/with_skill/grading.json"
python3 evals/grade_v4.py eval-8 "$D/without_skill" "$D/without_skill/grading.json"
# 然后按 evals/review-rubric.md 填各自目录下的 manual_review.md
```

> iteration-1..3 的夹具/评分器仍在（`build_fixtures.sh` / `setup_runs.sh` / `grade.py` / `run_grading.sh`），保留是为了让历史结论可追溯；
> **新一轮请用 iteration-4 这一套**（夹具设计与隔离机制都不同，数字不可混用）。

## 6. 与"确定性自测"的分工

| | `evals/test_scripts.sh` | 本文件的真实评测 |
|---|---|---|
| 测什么 | 脚本行为：布局/幂等/采纳/召回/体检/安装/打包/防泄露 | **模型行为**：给真实任务，agent 会不会照这套体系做 |
| 依赖模型 | ❌ 纯确定性（97 项） | ✅ 需要跑 agent |
| 何时跑 | 每次提交（CI + pre-commit） | 发版前 / 大改提示词与工作流后 |
